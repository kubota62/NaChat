NaChat バックアップと復元手順（Windows / Docker Desktop）
更新日：2026-11-17

対象：NaChatを動かすサーバーの担当者
社員が使うブラウザ側での操作は不要です。
以下の C:\work\NaChat は、実際にNaChatを置いたフォルダーへ読み替えてください。
コマンドはPowerShellで実行します。Docker Desktopは起動しておいてください。

1. どの方法を使うか
------------------------------------------------------------
通常は、付属の backup.ps1 / restore.ps1 を使います。

・DB：PostgreSQLのpg_dumpで database.dump に保存
・添付：mediaボリューム内のファイルを media.tar.gz に保存

添付は既に「ボリューム内のファイルを丸ごと保存する方式」です。
DBだけは、生のデータファイルのコピーではなくDB専用の形式で保存します。
DBと添付の対応を揃えるため、バックアップ中はチャットを一時停止します。
PostgreSQL自体は動かしたままpg_dumpを実行します。

【Dockerボリューム丸ごと保存との比較】
付属スクリプト：
  普段の保管、別PCへの移設、復元確認に適しています。
  PostgreSQLのファイル形式への依存が小さく、移設時に扱いやすい方式です。
  まず同じNaChat・PostgreSQLのバージョンに復元して確認してください。
  大量データの復元ではインデックス再作成などに時間がかかる場合があります。

DBボリュームを丸ごとコピー：
  DBを含めて停止し、同じ互換環境へ戻すための補助バックアップに向きます。
  通常のファイルコピーやtarで取得する場合は、PostgreSQLも停止が必要です。
  チャットだけを止めて、稼働中のDBボリュームをコピーしてはいけません。
  PostgreSQLのメジャーバージョン、拡張、ファイル所有権などの互換性が必要です。
  databaseとmediaの両方を、書き込みのない同じ期間に保存します。
  Dockerのエクスポート機能があるだけではDBの整合性は保証されません。

本書の復元コマンドは付属スクリプトで作ったバックアップ専用です。
Dockerボリュームの生コピーを restore.ps1 に渡すことはできません。

2. 何を保管するか
------------------------------------------------------------
毎回のバックアップで作られるもの：
  database.dump  アカウント、投稿、チャンネル、ログイン履歴、添付の管理情報など
  media.tar.gz   添付ファイル本体・プロフィール画像
  images.json    使用中イメージの情報（イメージ本体ではありません）

別途保管するもの：
  配布用一式（images.tar、compose*.yaml、infraフォルダーなど）
  .env（DBパスワードなど。公開フォルダーへ置かない）
  HTTPS運用時のcertsフォルダー（証明書・秘密鍵）
  独自変更した設定、利用中のComposeプロジェクト名、接続URL

イメージだけでは会話や添付は戻りません。
DBだけでは添付ファイル本体は戻りません。
Redisは通知・キャッシュ用のため、復元時に空で作り直します。
バックアップは機密情報として扱い、担当者だけがアクセスできる場所に保管します。

3. バックアップする
------------------------------------------------------------
(1) 利用者へ短時間の停止を案内します。
    同時に別のバックアップ、更新、復元を実行しないでください。

(2) PowerShellでNaChatのフォルダーへ移動します。

    cd C:\work\NaChat

(3) 現在運用している構成を指定します。
    以下は通常のプロジェクト名 nachat の例です。
    復元後に別名で運用している場合は、その名前に読み替えます。

    $env:COMPOSE_PROJECT_NAME='nachat'

    このPCだけのHTTP試用環境の場合：

    $env:COMPOSE_FILE='compose.yaml'

    HTTPSの社内公開環境の場合（上の行の代わりに）：

    $env:COMPOSE_FILE='compose.yaml;compose.lan.yaml'

    docker compose ps

    対象のapp・proxy・dbが起動していることを確認してください。

(4) バックアップを実行します。

    .\infra\backup.ps1

    処理内容：
      チャット停止 → DB保存 → 添付保存 → チャット再開

    スクリプト実行ポリシーで拒否された場合は、社内ルールを確認してください。
    自分で内容を確認したスクリプトの実行が許可されている場合のみ、
    このPowerShellウィンドウに限って次を設定し、再実行できます。

    Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass

(5) 結果を確認します。
    「Backup saved: ...」と表示されたフォルダーを開きます。
    例：C:\work\NaChat\backups\20261117T180000\
    database.dump、media.tar.gz、images.json が揃っていることを確認します。
    ファイルがあるだけで復元可能とは断定できません。手順4で復元確認します。

    docker compose ps

    チャットへログインし、通常利用が再開できることを確認します。
    エラーが出た場合は途中のファイルを正常なバックアップとして扱わず、
    app・proxyの起動状態を確認して、原因を解消してから取り直してください。

(6) 完成した日時フォルダーを別PC・NASなどへコピーします。
    同じPCのディスクだけに残すと、そのPCの故障時に一緒に失われます。
    定期実行・世代削除はまだ設定していません。
    例：1日分の損失を許容できるなら毎晩取得し、直近7回＋週次4回を保管。
    必要な頻度・世代数は社内の許容損失と空き容量に合わせて決めます。

4. 空の別環境へ復元し、確認する
------------------------------------------------------------
本番のデータを上書きせず、別Composeプロジェクトへ復元します。
同じPCでも実施可能です。本番とは別ボリュームを使うので容量が必要です。
以下は復元プロジェクト名を nachat-restore-check とする例です。
既にこの名前で復元済みの場合は nachat-restore-check2 など未使用の名前にします。
途中で失敗した復元先へ再実行せず、原因を解決して新しい名前でやり直します。

(1) 新しいPCへ復元する場合は、Docker DesktopをLinuxコンテナで起動し、
    バックアップ時に使用した配布用一式、.env、必要ならcertsを配置します。
    PowerShellで配置フォルダーへ移動し、イメージを読み込みます。

    cd C:\work\NaChat
    docker load -i .\images.tar

    開発用フォルダーではimages.tarがdist-release内にあります。
    同じPCで既に対象イメージがある場合、読み込みは不要です。
    まずバックアップ時と同じバージョンに戻し、更新は復元確認後に行います。

(2) 復元確認専用の構成に切り替えます。
    この指定は今開いているPowerShell内だけに有効です。

    $env:COMPOSE_FILE='compose.yaml;compose.restore-check.yaml'
    $env:COMPOSE_PROJECT_NAME='nachat-restore-check'

    この構成はホストPCの localhost:18080 だけにHTTPで公開します。
    本番の8080番・443番とは競合せず、社内LANには公開しません。
    compose.lan.yaml は復元確認時には混ぜないでください。

(3) 保存先を指定して復元します。日時部分は実際の保存先に置き換えます。

    .\infra\restore.ps1 -BackupDirectory 'C:\work\NaChat\backups\20261117T180000' -RestoreProject nachat-restore-check

    restore.ps1は空のDBにだけ復元します。
    スクリプトはDBとRedisを起動して復元しますが、チャット画面はまだ起動しません。
    「Restored into nachat-restore-check ...」の表示を確認します。

(4) 復元したチャットを起動します。

    docker compose -p nachat-restore-check up -d --no-build --pull never
    docker compose -p nachat-restore-check ps

(5) 同じPCのブラウザで開きます。

    http://localhost:18080

    バックアップ取得時点のアカウントとパスワードを使います。
    bootstrapやlocal_setupで管理者を新規作成する必要はありません。
    確認項目：
      ・ログインできる
      ・過去の投稿、チャンネル、DMが表示される
      ・添付ファイルをダウンロードして開ける
      ・登録済みのプロフィール画像が表示される
      ・管理者画面からログイン履歴が見える
      ・一般社員には非公開の会話や管理者向けログが見えない
      ・試験投稿と添付が利用できる（復元確認用データにだけ書き込まれる）

(6) 復元確認だけなら停止します。データは残ります。

    docker compose -p nachat-restore-check stop

    確認後はPowerShellを閉じるか、手順3の本番用環境変数に戻してください。
    本番のバックアップを復元確認用プロジェクトに対して実行しないよう注意します。

5. 復元した環境を本番へ切り替える場合
------------------------------------------------------------
・稼働中サーバーの移設なら、利用を停止して最後のバックアップを取り、
  それを新しい空の復元先へ戻します。古いバックアップ以降の投稿は戻りません。
・確認用データをそのまま使うと試験投稿も残ります。
・旧サーバーは停止し、同じ接続先で新旧が同時稼働しないようにします。
・本番用の.env（接続ホスト名/IP、ORIGINS等）と証明書を確認します。
・復元先のComposeプロジェクト名を維持して本番を起動します。
  名前を nachat に変えるだけではデータは移りません。

HTTPS本番への切り替え例（名前は実際の復元先に置き換える）：

    docker compose -p nachat-restore-check stop app proxy
    $env:COMPOSE_FILE='compose.yaml;compose.lan.yaml'
    $env:COMPOSE_PROJECT_NAME='nachat-restore-check'
    docker compose up -d --no-build --pull never

旧本番の443番が空いていること、証明書と.envが本番用になっていることが前提です。
社員用PCから本番URLへの接続、ログイン、投稿、添付を確認して利用を再開します。
以後の起動・停止・バックアップでも、このプロジェクト名を指定します。
切り替え後に新環境へ投稿があった場合、旧環境に戻すとその投稿は引き継がれません。

6. 避ける操作
------------------------------------------------------------
・通常の停止で docker compose down -v を実行しない。
  -v はデータボリュームを削除する指定です。
・Docker Desktopのボリューム削除・初期化をバックアップ前に行わない。
・バックアップ元の本番DBへ復元を試さない。
・稼働中のPostgreSQLデータを普通のファイルコピーでバックアップしない。
・.env、証明書の秘密鍵、バックアップを社員全員に公開しない。
